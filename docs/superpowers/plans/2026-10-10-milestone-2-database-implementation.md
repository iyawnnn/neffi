# Neffi Milestone 2 — Database Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:executing-plans (recommended here) or superpowers:subagent-driven-development to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Implement the real PostgreSQL/Drizzle data model for the locked Neffi system. That covers the Step 6 persistent concepts, critical integrity constraints, indexes for the known access paths, reviewed migrations on top of `0000_foundation_baseline`, Better Auth persistence wired through Drizzle, deterministic synthetic development seed data, database invariant tests, and an ERD generated from the migrated schema.

**Architecture:**
- One schema directory, `src/db/schema/`, split by domain area, using snake_case SQL through Drizzle `casing`.
- UUID primary keys generated by Postgres. Small, stable state sets are `pgEnum`s.
- DBC/GRC uses one `cards` table with a denormalized `kind` column, kept consistent by composite foreign keys and kind-guard CHECK constraints.
- The Card-owner = Profile-owner rule is enforced by a composite foreign key.
- Four small trigger guards (`cards_guard`, `activation_credentials_guard`, `history_guard`, `orders_guard`) cover the invariants that span old and new row values.
- Better Auth's `user`/`account`/`session`/`verification` models *are* Neffi's Account / Authentication Identity persistence. There is no parallel table.
- Invariant tests run against migrations applied from zero on in-process PGlite, so CI needs no database credentials. Live verification runs against `tapcard-dev`.

**Tech stack:** existing Next.js 16.4 / TypeScript / pnpm 11 / Drizzle ORM 0.45.4 + Drizzle Kit 0.31.11 / `pg` 8.23 / Better Auth 1.7.7 / Vitest 5 / Zod 4. New dev dependencies, both justified in §4: `@electric-sql/pglite` and `tsx`.

## 6. Conventions

**IDs:** `uuid().primaryKey().defaultRandom()` (`gen_random_uuid()`) everywhere, including the Better Auth tables via `generateId: "uuid"`. Exceptions:
- `orders.number`: `integer generated always as identity (start 1001)`, unique. This is the human order reference that Step 7 lists as an access path.
- Join table `support_case_cards`: composite primary key.

**Money and time:**
- Money is `integer` centavos (PHP only), with CHECK ≥ 0 or > 0.
- Owner-entered business dates are `date`: `paid_on`, `refunded_on`, `received_on`, `spent_on`, `shipped_on`.
- Audit times are `timestamptz` (`created_at defaultNow`, `updated_at` via `$onUpdate`).

**Enums** are `pgEnum` for locked, slow-changing state sets:

| enum | values | source |
|---|---|---|
| `account_role` | customer, owner | Step 7: OWNER via the same Account system |
| `product_kind` | dbc, grc | Steps 1/2 |
| `card_state` | blank, ready, reserved, released, retired | Steps 3/6 (Retired covers Defective) |
| `order_status` | in_progress, completed, cancelled | Step 3 |
| `delivery_method` | pickup, local_handoff, courier | Step 3 |
| `payment_method` | gcash, bank_transfer, cash | Step 3 (refunds reuse it) |
| `shipment_status` | pending, in_transit, delivered, failed, returned, lost | Step 3 "basic delivery state" + exceptions |
| `profile_status` | draft, published, unpublished | Locked Plan |
| `profile_link_type` | facebook, instagram, tiktok, linkedin, youtube, github, messenger, whatsapp, viber, telegram, x, portfolio, booking, shop, menu, custom | Step 2 |
| `expense_category` | inventory_production, shipping_delivery, packaging_printing, software_operations, marketing, other | Step 3 |
| `support_case_type` | activation_issue, account_recovery, ownership_correction, defective_card, shipping_issue, replacement, other | Step 5 |
| `support_case_status` | open, waiting_on_customer, resolved | Step 5 |
| `support_case_card_role` | affected, replacement | Steps 3/4 (free replacement links) |

`activity_events.type` is deliberately **text**, validated by a TS union in the activity module. Its vocabulary grows every milestone, and it is history rather than a state machine.

**Activation credential state** is not an enum. It is `used_at` / `revoked_at` timestamps, with "usable" meaning both are null. This gives state plus time with no redundant column.

## 8. DBC/GRC modeling decision

**Decision: one `cards` table with `kind`, five DBC-only columns guarded by CHECKs, and composite FKs. GRC destination data lives on the Order Item, not the card.**

`cards` columns:
- Identity and source: `id`, `stock_purchase_id` → stock_purchases (NOT NULL; Step 4 says every card traces to a purchase, and opening stock is an "opening" purchase).
- Product: `product_id?` + `kind?` → products(id, kind). Both are null while a blank card is uncommitted, because Step 4 says "optionally associated with its intended Product before sale".
- Lifecycle: `state card_state default blank`, `order_item_id?` + `product_id` → order_items(id, product_id). The card's product must be exactly the item's product.
- DBC-only: `public_token?` (unique), `owner_account_id?` → accounts, `profile_id?` + `owner_account_id` → profiles(id, account_id), `disabled_at?`.
- Timestamps.
- `unique(id, kind)` is the target of the credential FK.
- All composite FKs and CHECKs get explicit names so tests can assert the exact constraint.

CHECKs, all written to be NULL-safe: a CHECK that evaluates to NULL *passes* in Postgres, so every predicate on a nullable column is wrapped or guarded.
1. `(product_id IS NULL) = (kind IS NULL)`.
2. **GRC/uncommitted guard:** `COALESCE(kind = 'dbc', false) OR (public_token IS NULL AND owner_account_id IS NULL AND profile_id IS NULL AND disabled_at IS NULL)`. Only a DBC can carry a token, owner, profile or disabled flag, and that includes a card with no product yet.
3. `state IN ('blank','retired') OR product_id IS NOT NULL`.
4. `NOT COALESCE(kind = 'grc' AND state = 'ready', false)`, because GRC goes Blank → Reserved.
5. `kind IS DISTINCT FROM 'dbc' OR state IN ('blank','retired') OR public_token IS NOT NULL`.
6. `state NOT IN ('reserved','released') OR order_item_id IS NOT NULL`, and `state NOT IN ('blank','ready') OR order_item_id IS NULL`.
7. `profile_id IS NULL OR owner_account_id IS NOT NULL`. This is required because a composite FK under MATCH SIMPLE skips the check when any column is null.
8. `disabled_at IS NULL OR owner_account_id IS NOT NULL`.
9. **No ownership before sale:** `owner_account_id IS NULL OR state IN ('released','retired')`. An unsold card can't have an owner, so a cancelled reservation always returns an unclaimed card.
10. **Retired cards route nowhere:** `state <> 'retired' OR profile_id IS NULL`. Retiring a lost or defective card clears its profile, so it never blocks that profile's deletion.

**Why not subtype tables** (`cards` + `dbc_cards` + `grc_cards`):
- GRC adds no card-level columns at all. Its review URL belongs to the Order Item, per Step 3/4 "branch/location groups" and "destination belongs to fulfillment/item context". So `grc_cards` would be empty.
- A `dbc_cards` table would still need the same nullable lifecycle columns, since a token is null while blank and the owner is null until claimed. It would also need the same composite-FK trick to stop GRC rows.
- It would add a join to the hot `/c/{token}` lookup and to every inventory listing.

The single table with kind guards gives *equal* DB enforcement with fewer moving parts. The independent review found a NULL-`kind` bypass in the first draft of CHECK 2, now fixed with `COALESCE` and covered by a test. The DBC-only columns number four, plus `disabled_at`, so the table is not a "large weak table of unrelated nullables".

**Why not `review_url` on cards:** many cards share one URL per branch group, and a free GRC replacement links to the original item and inherits the same URL. That's exactly Step 3's model.

## 9. Account / Authentication Identity / Better Auth mapping

| Neffi concept | Physical table | Better Auth model | Notes |
|---|---|---|---|
| Account (permanent owner identity) | `accounts` | `user` | `id` (uuid) is the identity, never the email text. `email` is the primary verified sign-in email that Better Auth requires to be unique. `role` = customer/owner. |
| Authentication Identity (Google) | `auth_identities` | `account` | one row per linked provider identity, with unique `(provider_id, provider_account_id)`, so a Google identity can never attach to two Accounts. |
| Authentication Identity (email OTP) | `accounts.email` + `email_verified` (+ M3 rows in `auth_identities` if Better Auth creates them) | — | OTP challenges are transient rows in `auth_verifications`. |
| Session (not a business object, per Step 4) | `auth_sessions` | `session` | cascades with its account. |

There's one source of truth: no separate Neffi `accounts` table competes with Better Auth's `user`.

Wiring in `src/auth/server.ts`:
```ts
import { drizzleAdapter } from "better-auth/adapters/drizzle";
import { db } from "@/db";
import { accounts, authIdentities, authSessions, authVerifications } from "@/db/schema";

database: drizzleAdapter(db, {
  provider: "pg",
  schema: { user: accounts, account: authIdentities, session: authSessions, verification: authVerifications },
}),
advanced: { disableOriginCheck: false, database: { generateId: "uuid" } },
user: { additionalFields: { role: { type: "string", input: false, defaultValue: "customer" } } },
```
- Still no providers and no email/password, so nothing can create rows through HTTP in M2.
- Owner accounts exist only via the dev seed.
- Better Auth's `deleteUser` stays disabled, which is its default. Accounts are never hard-deleted, because `RESTRICT` FKs from orders, cards and profiles would block it anyway (§14).

## 10. Relationship and join-table decisions

- **Explicit FKs** for every known link, and no polymorphic `entity_type/entity_id`. Activity uses explicit nullable subject FKs, which Step 4 leaves to implementation.
- **Join table only where many-to-many is real:** `support_case_cards` (a case affects many cards; a card appears in many cases over time; the role distinguishes affected from free replacement).
- **Order Item → Cards** is `cards.order_item_id`, the card's commercial fulfillment link. A free replacement card points at the *original* item and appears in `support_case_cards` as `replacement`, so it's never a new sale. A paid replacement is a new Order and Order Item.
- **Refund/Shipment → Support Case** are optional FKs that tie support-driven money and shipping back to the case.
- **Purchaser ↔ Account:** no link, by locked rule.

## 11. Integrity rules: where each is enforced

| Rule | DB | App (milestone) |
|---|---|---|
| DBC token unique | unique index | — |
| DBC token permanent once issued | trigger `cards_guard`: token can't change once non-null | M4 generates it |
| Token is not a secret | no secret columns on cards; credentials in a separate table | M5/M7 never treat it as proof |
| Credential unused→used / unused→revoked, never re-enabled | CHECK (not both) + trigger `activation_credentials_guard`: `used_at`/`revoked_at` can't change once set; `card_id` and `lookup_hmac` immutable; DELETE forbidden | M4/M5/M9 |
| ≤1 usable credential per card | partial unique index | M4 revokes the old one before issuing in the same tx |
| Credentials only for DBC | composite FK `(card_id, card_kind='dbc')` | — |
| No plaintext secret stored | `lookup_hmac` CHECK of 64-char lowercase hex (a raw code can't satisfy it) | M4 HMAC key and format |
| ≤1 current owner / ≤1 current profile | single columns on `cards` | — |
| Card can't route to another Account's Profile | composite FK `(profile_id, owner_account_id) → profiles(id, account_id)` + CHECK 7 | M6 also checks before writing; M9 corrections disconnect then reconnect |
| Ownership separate from routing | separate columns, independently nullable | — |
| GRC has no owner/profile/token/credential | CHECK 2 + credential composite FK | — |
| Card product matches order item product | composite FK `(order_item_id, product_id) → order_items(id, product_id)` | — |
| No owner before sale; retired cards route nowhere | CHECKs 9 and 10 | M5 claims only released cards; M9 retire clears the profile |
| Released never returns to inventory; Retired terminal | trigger `cards_guard`: `released` → only `retired`; `retired` → no change of state; DELETE allowed only for `blank` | M8 cancellation releases only `reserved` cards. An encoded GRC goes to `retired` and an unencoded one to `blank`. A courier return/loss → `retired` + replacement |
| Payments, refunds, activity are append-only history | trigger `history_guard`: DELETE forbidden on payments, refunds, activity_events | M8: corrections are new rows; voiding a mis-keyed payment is an M8 decision (R10) |
| Historical pricing | `order_items.unit_price` / `agreed_total` snapshots, separate from `products.price` | M8 copies at creation |
| Payments/Refunds historical, separate | separate tables, positive CHECKs, FK RESTRICT (orders with money can't be deleted) | M8: no delete paths; corrections are new rows |
| Order requires purchaser | NOT NULL FK | — |
| Order lifecycle states; Completed/Cancelled final | enum + timestamp CHECKs + trigger `orders_guard` (terminal states) | M8 completion service is the only writer of `completed` and re-derives eligibility in the same tx (§13); cancellation only while `in_progress` and no released card |
| Completion not driven by activation | no FK or column couples them | — |
| Inventory counts derived | no count/total columns anywhere | M8 aggregates `cards` |
| Profile deletion blocked while cards connected | FK `cards.profile_id` RESTRICT | M6 UX |
| Account deletion doesn't free cards | FK RESTRICT from cards/orders/profiles; sessions/identities cascade | M3/M9 restriction flow |
| Atomic claim / correction / reservation / financial / replacement | §15 | M5/M8/M9 transactions |

Multi-entity rules M2 does **not** fake in SQL (app plus tests in their milestones):
- refund ≤ net paid;
- cancellation only with no released card;
- completion eligibility;
- GRC item has a `review_url` before its cards are reserved;
- owner role required on `created_by`/`assigned_to`;
- a support case has ≥ 1 card when its type requires one.

## 13. Stored vs derived

**Stored (canonical):**
- catalog price;
- item price snapshots and optional agreed total;
- shipping fee charged;
- payments and refunds;
- shipment courier cost;
- stock purchase and inbound shipping costs;
- manual expenses;
- all lifecycle states and their timestamps;
- card owner and card profile.

**Derived (never stored):**
- item effective total `coalesce(agreed_total, quantity * unit_price)`;
- order total (sum of effective totals + shipping fee);
- amount received, refunded and net paid;
- balance and refund due;
- Paid/Unpaid;
- inventory counts;
- stock purchase quantity;
- completion *eligibility*;
- expense report totals;
- dashboard metrics.

**Order completion: the source-of-truth reading.**

Exact wording, from this session's Notion fetches:
- **Step 6, Critical Integrity Rules:** "Order lifecycle remains In Progress, Completed, or Cancelled. Completion is **system-derived** from full seller fulfillment plus zero balance."
- **Step 6, Stored vs Derived:** *Store* "…**Order**/Card/Profile/Support/Credential **lifecycle state**…"; *Derive* "…**completion eligibility**…".
- **Step 6, Stored-vs-Derived Examples:** *Store* "**Order lifecycle state**"; *Derive* "**Order completion eligibility**".
- **Locked Plan, Step 6 direction:** "Store canonical facts/state and derive balances, payment state, inventory counts, **completion eligibility**, and dashboard summaries."
- **Step 5, Orders rule:** "Totals, balance, payment state, normal card-state transitions, seller-fulfillment state, and completion should be **derived from business actions rather than manually maintained statuses**."
- **Step 3:**
  - "If the customer buys again **after the order is already Completed**, create a new order."
  - "A **Completed order may still have a shipment exception** that requires support follow-up."
  - Cancellation is allowed only for an In Progress order.

**Interpretation.** The source names two different things.
- The **lifecycle state** (In Progress / Completed / Cancelled) is *stored*.
- **Completion eligibility** (fulfillment + zero balance) is *derived*.

"System-derived" and "derived from business actions rather than manually maintained" say *who decides*: the system, by evaluating the facts, never a person editing a status. They don't say the state is recomputed forever. A purely computed status would also contradict Step 3. A Completed order that later gets a refund, a shipment exception, or a defective card retired for a free replacement (Step 4 #9/#10) would silently revert to In Progress. That breaks "Completed is terminal; later purchases are new orders" and lets a Completed order become cancellable.

**Design (kept), and why it isn't duplicated truth.**
- `orders.status` + `completed_at` record **one historical event**: "at `completed_at`, the system established eligibility". Eligibility is a predicate over the *current* facts. They answer different questions ("was this order completed?" versus "would it qualify now?"), so a later refund or replacement can't create a contradiction.
- The only writer of `completed` is the M8 completion service. In one transaction it locks the order, recomputes eligibility from items, cards, shipments, payments and refunds, and sets `status = 'completed', completed_at = now()` only if eligible. There's no manual or UI path. This matches Step 5's "not manually maintained".
- **DB guard (added to `0005`):** `orders_guard` makes `completed` and `cancelled` terminal: neither can be changed or reverted. The existing CHECKs tie each status to its timestamp. So once written, the transition can't be flipped by hand.
- The **disagreement window** is "eligible but not yet marked". It's closed by M8 evaluating completion inside every transaction that changes the inputs (payment recorded, cards released, shipment handed over). Until then, the order is correctly In Progress.

No stored `paid`, `balance`, `fulfilled` or `eligible` column exists, so the facts stay the only source for eligibility.

**Expenses keep one source of truth per cost.**
- Stock purchase costs live on `stock_purchases`, and courier cost lives on `shipments`.
- `expenses` holds only manually entered costs, optionally linked to an order.
- Expense reporting (M8) is a UNION of the three sources, so the same amount is never stored twice. This follows Step 6 ("a cost should have one source of truth… feed expense reporting") over Step 3's "create/link an expense automatically" wording. Approved as decision D1 (§21).

## 14. Deletion, archive and history

- **Default FK `ON DELETE RESTRICT`.** Nothing commercial, physical or historical cascades.
- **Cascades only where the child has no independent history:**
  - `auth_identities` and `auth_sessions` → account;
  - `profile_links` → profile;
  - `support_case_cards` keep RESTRICT.
- **Row-level guards (triggers):** cards can be deleted only while `blank`. Credentials, payments, refunds and activity events can't be deleted. The dev seed reset uses `TRUNCATE`, which row triggers don't intercept, so the seed still works.
- **Retire rather than delete:**
  - cards → `retired`;
  - credentials → `revoked_at` (DELETE blocked by trigger);
  - support cases → `resolved`;
  - orders → `cancelled`;
  - profiles → `unpublished` (deletion allowed only with no connected cards);
  - accounts → never hard-deleted in M2+.
- **Account deletion/restriction (M3/M9):** expected to add a nullable `accounts.restricted_at`/`deleted_at` plus email anonymization, since the unique email would otherwise block re-signup. That's additive, so it isn't built now.
- No soft-delete columns are added speculatively.

## 15. Transaction boundaries the schema supports (implemented later)

| Workflow | Rows touched in one tx | Schema support |
|---|---|---|
| Card claim (M5) | `SELECT … FROM activation_credentials WHERE lookup_hmac=$1 FOR UPDATE` → card row `FOR UPDATE` → set `cards.owner_account_id` (where null) → set `used_at` → insert activity | partial unique and row locks; trigger blocks re-use |
| Ownership correction (M9) | card: clear `profile_id` + `owner_account_id`; revoke usable credential; insert new credential; activity | CHECK 7 allows clearing both in one UPDATE; partial unique requires revoke before insert |
| Profile move between accounts (M9, support) | disconnect cards → update `profiles.account_id` → update card owners → reconnect | composite FK forces explicit, ordered steps |
| Multi-card reserve/release (M8) | `UPDATE cards SET state, order_item_id … WHERE id = ANY($1) AND state = 'ready'` with row-count check | state CHECKs + kind FK |
| Financial ops (M8) | payment/refund insert + activity (+ order status) | separate tables, no aggregates to keep in sync |
| Free replacement (M9) | retire affected card; reserve/release replacement against the original item; `support_case_cards` rows; optional shipment/refund with `support_case_id`; activity | all FKs present |

The runtime `pg` Pool already supports interactive `db.transaction`. Neon's pooled endpoint runs in transaction mode, so session-level features aren't used.

## 18. ERD

## 19. Test strategy

**Harness:** `src/db/testing.ts`
- `createTestDb()` creates a PGlite instance, runs `migrate(db, { migrationsFolder: "drizzle" })` on `drizzle({ client, schema, casing: "snake_case" })`, and is shared per test file.
- `rollback(fn)` runs each test inside a transaction that is always rolled back.
- `expectPgError(tx, fn, code, constraint?)` runs the failing statement inside a **nested `tx.transaction` (savepoint)**. Without it, the first expected error would abort the outer transaction (25P02) and poison every later statement. It asserts SQLSTATE (`23505` unique, `23503` FK, `23514` check, `P0001` trigger) plus the constraint name, not just "it threw".
- The Better Auth round-trip uses the same options as production. `src/auth/options.ts` (pure, no `server-only`) exports `authOptions({ db, secret, baseURL })`. `server.ts` passes the real `db` and env; the test passes the PGlite db.
- Files are named `*.db.test.ts` and run in the normal `pnpm test`, so they run in CI without credentials.

**Invariant tests**, each must fail before its constraint exists (TDD red → green per task):
- **Migrations:** baseline + M2 apply from zero; `db:generate` reports no drift (CI step); the guard triggers exist.

## 21. Risks and ambiguities

- **R1. PGlite (PG 17) vs Neon (PG 18).** Every feature used (partial indexes, composite FKs, CHECK, plpgsql triggers, `gen_random_uuid`, identity) exists in both. Row 7 and row 10 on real Neon are the backstop. If PGlite + Drizzle 0.45 misbehaves (Task 1 spike), the fallback is DB tests against a dedicated Neon dev *branch* via `DATABASE_URL_TEST`, skipped in CI. That would be raised before proceeding.
- **R2. Better Auth field and model mapping.** Using Better Auth's logical JS keys with custom SQL names, and modelName keys in the `schema` object, is supported by the adapter code read here (1.7.7). Its runtime schema check plus the round-trip test prove it. A future M3 `admin` plugin expects `role` as text with "admin"/"user". If M3 adopts it, the role column may need a reviewed migration (flagged, not designed for now).
- **R3. Blank cards without a product.** Step 4 says the product association is optional before sale, so `product_id`/`kind` are nullable only while blank or retired. If the business assigns kind at stock receipt instead, a later migration can make them NOT NULL.
- **D1. Expenses (approved, locked).** Stock-purchase and courier costs stay on `stock_purchases`/`shipments`. `expenses` holds only manual entries. Reporting combines the canonical sources. The same cost is never copied into an Expense row.
- **D2. Order completion (resolved from source, §13).** The lifecycle state is stored, eligibility is derived, the system is the only writer, and Completed is final.
- **R6. Triggers live in a custom migration** that Drizzle's snapshot doesn't model. They're documented in the ERD catalog and covered by tests. Kept to four guards for locked security, inventory, history and order-lifecycle invariants.
- **D3. Card lifecycle (approved, locked).** A Released card never returns to ordinary inventory. `released → retired` is the only exit, and `retired` is terminal. History is preserved; physical cards are not recycled.
  - A courier return or loss retires the card, and a replacement is issued.
  - An encoded-then-cancelled GRC is retired; an unencoded reserved GRC goes back to `blank`.
- **D4. Mis-keyed payments (approved deferral to M8).** M2 designs no void/correction behavior. M2 doesn't block a clean additive mechanism either:
  - `history_guard` blocks DELETE only, so M8 can add nullable `voided_at`/`void_reason` (or correction rows) with a normal migration and exclude voided rows from derived totals.
  - `amount > 0` stays valid under either option.
  - A test proves an added nullable column can be set on an existing payment.
- **R7. `accounts.email` is required and unique** (Better Auth core). This is consistent with Google and email OTP (both yield a verified email). The M3 identity-linking rules sit on top.
- **R8. The dev seed truncates `tapcard-dev` tables** (documented). The dev DB holds only synthetic data by rule.
- **Manual step (you):** before Task 9, create a Neon branch or snapshot of `tapcard-dev` named `pre-m2` in the console.
